# 작업 순서와 프롬프트

팀원 누구나 Claude Code에 같은 순서로 일을 시키기 위한 문서다.
한 번에 한 단계만 한다. 단계가 끝나면 아래 상태 표를 고치고 커밋한다.

## 2. 규칙

- **한 번에 한 단계.** 단계가 끝나면 상태 표를 고치고 커밋한다. 잘못되면 그 커밋으로 되돌린다.
- **0단계와 1단계의 결과는 기획 담당에게 공유한다.** 기획 담당이 그 결과로 `docs/SPEC.md`, `docs/UI_SPEC.md`를 고친 다음에 2단계로 넘어간다.
- **큰 단계(2, 3, 4)마다 새 대화로 시작해도 된다.** Claude Code는 대화를 시작할 때 `CLAUDE.md`를 읽고, `CLAUDE.md`가 docs의 명세를 가리킨다. 대화가 길어지면 응답이 느려지고 앞의 내용을 놓치기 쉽다.
- **1차 마감은 2026-11-15 23:59다.** 시연 영상은 선택(가산점)이다. 2~4단계가 마감 전에 끝나지 않으면 영상 없이 제출하고, 기획서 일정표의 "1차 제출: 에뮬레이터 시연 영상" 줄을 고친다.
- 커밋 작성자 이름·이메일에 실명이 들어가지 않게 한다 (공모전 규칙).

## 3. 단계별 프롬프트 (그대로 복사해서 넣는다)

### 0단계: 화면 없을 때 수신 확인 결과 보고와 커밋

```
3번 결과(앱 화면이 없을 때 차량 값을 받는지)를 "된다 / 안 된다 / 조건부"로 정리해서 보고해. 그다음 지금까지의 변경(docs 폴더, CLAUDE.md, 코드)을 커밋해. 커밋 작성자가 팀 이름으로 되어 있는지 확인해.
```
끝난 기준: 결과가 상태 표의 메모 칸에 적혀 있고, 커밋이 있다.

### 1단계: 명세 검토 (코드는 고치지 않는다)

```
docs/SPEC.md, docs/UI_SPEC.md, docs/design/REFERENCES.md를 읽어. 코드는 아직 고치지 마.
1. 지금 코드나 SDK에서 확인한 사실과 맞지 않는 부분을 찾아.
2. 규칙이 모호해서 두 가지로 구현될 수 있는 부분을 찾아.
3. 【확인 필요】 중에서 지금 확인할 수 있는 것(WiperState·LightState enum 값, 브레이크 페달 값의 형식, 앱 창 크기 dp와 밀도)은 AAR이나 에뮬레이터로 확인해서 답해.
목록으로 짧게 보고해.
```
끝난 기준: 보고를 기획 담당에게 공유했고, 명세가 고쳐졌다.

### 2단계: 판정 로직 (M1)

```
docs/SPEC.md의 M1 판정 로직을 구현해. Plan 모드로 계획부터 보여 줘.
순서: (1) domain 패키지(TripRecorder, SafetyScore, Encounter, Residents, Points, TimeSource, RandomSource)와 단위 테스트를 만들고 testDebugUnitTest 통과 (2) VehicleDataSource에 브레이크와 주행 규제를 추가하고, 조향각과 브레이크는 이벤트 흐름으로도 내보내 (3) RecordingService에 연결하고 JSON 파일로 저장 (4) 디버그 메뉴(시간 배율, 시연 데이터 불러오기, 데이터 초기화).
주민은 비 → 가족 → 밤 → 겨울 순서로 하고, 단계마다 빌드와 테스트를 돌려.
화면은 아직 만들지 마. 판정 결과는 logcat과 진단 화면으로 확인해.
```
끝난 기준: 단위 테스트 통과. 에뮬레이터에서 기어 D → 와이퍼 → 기어 P를 했을 때 logcat에 안전 점수와 판정 결과가 찍힌다.

### 3단계: 화면 (v2 깔끔한 미니멀 시안, 완료)

```
docs/UI_SPEC.md와 docs/design/REFERENCES.md를 읽고, docs/design의 시안 PNG와 mockups.html을 확인해. Plan 모드로 계획부터 보여 줘.
1. 디자인 시스템부터 만들어: 색 토큰(낮·밤), Pretendard 글꼴(res/font), 카드·주 버튼·보조 버튼·칩·분할 버튼·내비게이션 레일·점수 링 컴포저블. 부품마다 @Preview를 붙여.
2. mockups.html의 blob(), house(), tree(), fountain(), lamp(), village() 좌표를 Compose Canvas로 옮겨. 시안 PNG와 나란히 비교할 수 있게 미리보기를 만들어.
3. 그다음 UI_SPEC 7장 순서대로 도착 요약 → 마을 → 도감을 만들어. FakeRepository로 시안 데이터를 넣고, 넓은 배치·좁은 배치 미리보기를 붙여.
4. 단계마다 빌드하고 에뮬레이터 화면을 캡처해서 시안과 비교해. 다른 점을 목록으로 보고해.
```
끝난 기준: 도착 요약, 마을, 도감이 시안과 비슷하게 보인다. 넓은 배치와 좁은 배치 모두 깨지지 않는다.

### 3b단계: 디자인 v4(파스텔 선화)로 바꾸기

```
docs/design/REFERENCES.md(v4)와 docs/UI_SPEC.md 0장 6번, 5장을 읽고, docs/design의 새 시안 PNG와 mockups.html을 확인해(밤 모드는 mockups.html?theme=night). Plan 모드로 계획부터 보여 줘.
1. ui/design의 색 토큰(낮·밤)과 글꼴을 v4로 바꿔. Jua(제목, 주민 이름, 말풍선)와 Pretendard(본문)를 res/font에 넣어. 라이선스 파일은 docs/licenses에 둬.
2. 부품을 v4로 바꿔: 흰 카드 + 2dp 외곽선(그림자 없음), 외곽선 있는 주 버튼·보조 버튼, sel 바탕 메뉴·탭, 톱니 가장자리 우표 카드, 네모 서랍 카드, 외곽선 말풍선, 80점 선이 있는 점수 막대. 부품마다 @Preview를 붙여.
3. ui/art의 주민과 마을 그림을 mockups.html의 그림 함수로 다시 옮겨. 모든 Path는 채운 다음 2dp 둥근 끝 선으로 그려. 주민마다 몸 모양이 다르고, 주민 집은 주민 모양을 따른다.
4. 도착 요약 → 마을 → 도감을 새 시안처럼 바꿔. 기능과 데이터 흐름은 바꾸지 마. 단계마다 빌드하고 에뮬레이터 화면을 캡처해서 시안과 비교해. 다른 점을 목록으로 보고해.
```
끝난 기준: 도착 요약, 마을, 도감이 새 시안과 비슷하게 보인다. 명암비 4.5:1 이상. 넓은 배치와 좁은 배치 모두 깨지지 않는다.

### 4단계: 실제 데이터 연결과 시연 확인

```
FakeRepository 대신 실제 Repository를 연결해. 그다음 docs/SPEC.md 10장의 시나리오 A와 B를 나와 같이 에뮬레이터에서 확인하자. Virtual Console은 내가 조작할게. 단계마다 무엇을 누르면 되는지 알려 줘.
```
끝난 기준: 시나리오 A(레이니·해삐 만남)와 B(70점, 주민 없음)가 에뮬레이터에서 그대로 동작한다.

## 4. 그다음 (M2, 2차 PT 전까지)

UI_SPEC 7장의 6~8단계(기록, 설정, 시작 안내, 꾸미기, 새 주민 직접 배치, 좁은 배치 점검)와 SPEC 2장의 M2 범위(장거리·충전 주민, 시나리오 C·D)를 같은 방식으로 한 단계씩 진행한다. 이 문서에 단계를 추가해서 관리한다.
